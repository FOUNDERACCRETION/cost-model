# MLIP relaxation timing benchmark: protocol and results

Generated by `benchmarks/mlip/report.py` from `timings.csv`, `throughput.csv`, `run_log.txt`, `m3gnet_diagnosis.txt`,
`production_m3gnet_convergence.json` and `matbench_discovery/*.yml`; every number in the text is computed from these at
write time. Raw data: `timings.csv`
(one row per relaxation, every attempt including failures), `throughput.csv` (one row per concurrent test).

**What this measures:** the compute cost of relaxing candidate structures with three ML interatomic potentials on
CPU. Every energy in the data is an **ML prediction, not DFT**; nothing here is DFT-verified. Accuracy is not
measured. **This is CPU-only inference with the torch `+cpu` build** (no GPU, no CUDA packages installed).

## 1. Headline: cost per relaxation (primary configuration, 1 thread)

The cost model is denominated in core-hours, and cloud instances bill per allocated vCPU whether a thread does useful
work or spin-waits, so `core_hours = threads_actual × wall_clock_s / 3600` is the quantity to minimise. On this machine
that minimum is **1 thread(s)** in every sweep group (§8), so the primary dataset is
`config=primary_1thread` (1 thread). The native-candidate summary
excludes the non-native 56-atom supercell:

| model | native structures | converged | mean core_hours | median core_hours | min | max | core_hours per atom (pooled) |
|---|---|---|---|---|---|---|---|
| chgnet | 6 | 6 | 0.0012 | 0.000892 | 0.000392 | 0.0022 | 5.9e-05 |
| mace-mp-0 | 6 | 6 | 0.0070 | 0.0059 | 0.0020 | 0.0132 | 0.000348 |
| m3gnet | 6 | 1 | 0.0083 | 0.0074 | 0.0021 | 0.0145 | 0.000417 |

**Read the M3GNet line with care:** 5 of its 6 native relaxations hit the
500-step cap without converging (§7.1), so its cost is set by `max_steps`, not by convergence, and is not a
cost per *completed* relaxation. Its per-step cost (`time_per_step_s`) is the transferable number. CHGNet and MACE-MP-0
converged on every structure in both matrix configs.

**Two factors, not one.** Every row also carries `core_seconds_per_ionic_step` (= threads_actual × wall_clock_s /
n_ionic_steps). Per-step cost grows roughly linearly with N (§7, log-log slope of time per step 0.89–1.05
across the three models), while the number of ionic steps (18–81 for the CHGNet/MACE matrix runs) rises
with size less steeply (log-log slope 0.72 CHGNet, 0.66 MACE, the gap between the core_hours and time_per_step
slopes in §7) and with scatter by structure. *Corrected 2026-10-22: this line previously said steps vary
"independently of size", which the §7 table contradicts.* A cost model
should therefore use cost per relaxation = (core-seconds per step at N) × (steps), with the two factors taken separately.

**Parallel throughput is not a parameter of this study.** Concurrent workers on this platform hit a WSL2/Hyper-V
memory-handling artefact (§9), so the cost unit for the paper is the serial single-thread core-hours per relaxation above.

Model load time (one-off per process, 0.8–5.8 s here) and the untimed warm-up are **not** included in
`wall_clock_s` or `core_hours`; they're recorded in `model_load_s`. In a long-running worker they amortise to zero; for
one-shot jobs add them.

## 6. Run design

**Relaxation settings** (identical to the production pipeline, `astral/config.py`): ASE `FIRE` optimiser on
`FrechetCellFilter(atoms)` (positions **and** cell relaxed together, default filter arguments), `fmax = 0.05` eV/Å
(forces and filter cell degrees of freedom), `max_steps = 500`. MACE in float64. CHGNet with the
default `stress_weight` (GPa → eV/Å³); M3GNet via `PESCalculator(..., stress_unit="eV/A3")`. The production
guardrails (volume ±50%, minimum distance) are **not** applied, so every run is a complete relaxation. ASE is called
directly, not through `relax_candidate()`, which reads and writes the result cache.

**Process isolation:** every relaxation runs in a fresh Python subprocess, one at a time (serial; nothing else
heavy ran on the machine during timed runs). Order inside a worker: set threads, load model (timed → `model_load_s`),
untimed warm-up single point (energy, forces, stress) on the warm-up structure, timed relaxation.

**Threads:** the parent sets `OMP_NUM_THREADS`, `MKL_NUM_THREADS` and `OPENBLAS_NUM_THREADS` to the requested count
before the worker imports torch, and the worker calls `torch.set_num_threads(n)` and `torch.set_num_interop_threads(n)`.
`threads_actual` and `interop_threads_actual` are what torch reports afterwards. This bypasses
`astral.screen.potentials.get_calculator()`, which would force `ASTRAL_TORCH_THREADS` (default 4). The aarch64 torch
wheel does not use MKL, so `MKL_NUM_THREADS` is recorded but has no effect. `threads` = `threads_requested` = the env
value.

**Measurements:** `wall_clock_s` = `time.perf_counter()` around `opt.run()`. `cpu_time_s` = user + system CPU time of
the worker process (all threads) over the same interval (`getrusage`). `n_ionic_steps` = `opt.nsteps` (FIRE does one
force/stress evaluation per step plus one initial). `time_per_step_s` = wall / steps. `peak_rss_mb` = `ru_maxrss` of
the worker process over its whole life (model + warm-up + relaxation), i.e. the memory a job needs.
`core_hours` = `threads_actual × wall_clock_s / 3600`. `converged` = ASE's return value (fmax reached within
max_steps). `volume_change` = V_final / V_initial − 1.

**Configurations and counts:**

| config | threads | what | runs |
|---|---|---|---|
| `primary_1thread` | 1 | all 7 structures × 3 models; NaMnF3 repeated (repeat_index 0–2) | 27 |
| `secondary_4thread` | 4 | same as primary | 27 |

### 7.1 M3GNet non-convergence (diagnosed, not a configuration bug)

M3GNet hit the 500-step cap on 6 of 7 structures
(primary) and 6 of 7 (secondary); CHGNet and MACE-MP-0 converged
everywhere (18–81 steps). `diagnose_m3gnet.py` (output in `m3gnet_diagnosis.txt`) tested the two candidate
artefacts on frame-0 TiSiN2:

- **Stress units: not the cause.** M3GNet's max |stress| is 1.27× the mean CHGNet/MACE magnitude
  (a units bug would make it ~160.21766208× off), its calculator conversion factor is 0.00624151 (=
  1/160.21766208, GPa → eV/Å³, applied once), and its analytic stress matches a finite-difference stress from
  its own energies on the diagonal (ratios 1.015, 1.032, 0.998).
- **Warm-up on a shared calculator: not the cause.** Relaxation traces
  with and without the warm-up are identical to every printed digit.
- **What happens:** at step 50 M3GNet's volume change is -12.4% (CHGNet's final:
  -14.2%); then the FIRE timestep collapses. From step 100 on, the same
  energy and fmax (0.6709 eV/Å) recur at 94% of the sampled
  steps, i.e. the geometry stops moving. M3GNet's finite-difference *shear* stress is unphysical
  (-103–-64 eV/Å³ for a tiny strain), which suggests its energy is not smooth under small
  shear at this geometry (it runs in float32). This was not diagnosed further.

So the M3GNet rows measure a real failure mode of this checkpoint (`M3GNet-PES-MatPES-PBE-2025.2`) with FIRE +
FrechetCellFilter from raw substitution geometries, not a broken configuration; they stand as data. The production
pipeline never showed this because it starts M3GNet from CHGNet-relaxed structures
(30 of 445 cached production M3GNet relaxations hit the cap from
those starts; `production_m3gnet_convergence.json`).

### OMP_WAIT_POLICY diagnostic (one run)

CHGNet, NaMnF3, 12 threads. Sweep run (default wait policy): wall 11.78 s, cpu 73.0 s (cpu/wall 6.20). With `OMP_WAIT_POLICY=passive`: wall 11.79 s, cpu 22.2 s (cpu/wall 1.88), 18 steps.

Passive waiting cut CPU time from 73.0 s to 22.2 s while wall time went from 11.78 s to 11.79 s. So OpenMP spin-waiting explains the burned CPU time (cpu/wall 6.2 at 12 threads) but **not** the slowdown itself. Across the sweep, 1 thread is the core-hour optimum in every case. The wall-clock optimum is 2–6 threads for CHGNet and MACE-MP-0 (speedup at most 1.88×, costing 1.6–3.2× the core-hours) and 1 thread(s) for M3GNet. At 12 threads every model is slower than at 1 thread (speedup 0.13–0.37, costing 32–90× the core-hours). CHGNet speedup at 4 threads: 1.53 on the 56-atom cell vs 1.16 on NaMnF3.

**Even if passive waiting lowers CPU time, it does not lower billed core-hours**: billing follows allocated vCPUs, and
an n-vCPU allocation is billed for n vCPUs whether its threads spin, sleep or compute.

## 9. Limitations: parallel throughput is unmeasurable on this platform

A 12-worker concurrent test (single-threaded processes) ran 43× worse
in effective core-hours per relaxation than the same jobs run serially (`throughput.csv`). On the live run, every worker
was verified single-threaded, yet most CPU time was kernel time driven by minor page faults, with no major faults and no
steal time (observed values in `run_log.txt`; not saved as data, so not quoted here). This is a WSL2/Hyper-V
memory-handling artefact, not a property of MLIP screening, so no cost figure is derived from it. The one completed
point (CHGNet) is kept in `throughput.csv` and `timings.csv` (`config=throughput_12x1_contaminated`) marked
contaminated; it also started at load average 4.6 instead of idle.

## 10. Hardware generalisability

This machine is a **Qualcomm Snapdragon X (Oryon, 12 cores, ARM64) Surface Pro 11 running Linux under WSL2**
(Hyper-V virtual CPUs), with 15.4 GiB RAM visible to WSL, on a fanless tablet chassis. CPU frequency is not exposed inside
WSL2, so throttling could not be measured. The thread-scaling cliff measured in §8 may be specific to this platform: the
Snapdragon X groups its cores in clusters, WSL2 puts a virtual-CPU scheduler between the OpenMP runtime and the
hardware, and the same memory-handling artefact seen in §9 may contribute. A bare-metal x86 server or a cloud vCPU instance may
scale differently. **The single-thread core-hour figures (§1) are the most portable numbers for the cost model**: they
involve no inter-thread synchronisation, so they depend mainly on single-core speed. Even so, single-core speed differs
between this laptop core and a cloud vCPU, so absolute values should be treated as indicative of this hardware class.

## 12. Deviations from the original request

- The original plan ran the main matrix at 12 threads. After the first row (now `config=initial_12thread`)
  ran 9.0× slower than the same relaxation at 1 thread, the primary configuration moved
  to 1 thread (core-hour optimal), with 4 threads (wall-clock optimal) as secondary, a sweep and a throughput test
  added. The CHGNet diagnostic runs at other thread counts made before that decision are recorded in `run_log.txt` only,
  not in `timings.csv`; the sweep replaces them with controlled runs.
- The plan said one subprocess per model; each relaxation instead gets its own subprocess, so `peak_rss_mb` belongs
  to one run and repeats are independent.
- The 56-atom thread sweep was trimmed to CHGNet only (overnight time budget, user decision). The driver was stopped
  and restarted for this trim; the in-flight run was discarded and rerun (see run log).
- The throughput test was stopped after CHGNet (contaminated, §9); MACE was killed mid-run with no rows written, and
  M3GNet and the planned worker-count sweep were not run (user decision: throughput is a limitation, not a parameter).
- The largest native candidate has 32 atoms; 56 atoms is reached only with the non-native
  supercell.
